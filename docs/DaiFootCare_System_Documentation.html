1  System overview

DiaFootCare helps people with diabetes monitor foot ulcers and helps their clinicians supervise that monitoring remotely. It has three cooperating parts:

ComponentWho uses itWhat it doesStack
Mobile appPatients / carers Photographs a wound and analyses it on the device or via the server; tracks healing; holds daily self-care, glucose, medication, appointments, reminders and well-being. Flutter (Android), on-device TFLite, local SQLite
Web dashboardClinicians / study team Reviews every patient's scans, healing trends, risk alerts, devices and engagement; exports study data. Laravel 12 API + Vue 3 SPA (Sanctum auth)
Inference server(internal) Runs the same three models server-side for patients who chose not to download them. FastAPI + TFLite sidecar
Table 1. The three components of the platform.

1.1  Two ways to analyse, one result

Analysis runs on the phone (offline, after a one-time ~200 MB model download) or on the server (online). Both paths run the identical models and the identical measurement post-processing, so a wound yields the same result either way. Each result records which path produced it. The patient chooses the mode at first launch and can change it later.

1.2  What the AI reports

From a single photograph the app produces wound measurements (length, width and surface area), the tissue types present in the wound bed, and two clinically-validated risk indicators — infection and ischaemia (blood flow) — combined into a single risk badge. The models themselves are documented in depth in the companion three-model technical reference; Section 4 summarises them.

Privacy by design

In offline mode a wound photograph never leaves the phone. In online mode it is sent over an encrypted connection and the patient gives explicit, informed consent first (Section 2.1). Records sync to the clinician dashboard only for registered patients; the app is fully usable as a guest with everything kept on-device.

2.3  Wound capture & AI analysis

The core flow is fast: photo guidance → capture (or pick a photo) → confirm → analysis. Three models run — segmentation for measurements, tissue classification, and infection/ischaemia — and the result screen shows the wound's length, width and surface area, the tissue types in the wound bed with confidence, the infection and blood-flow status, an overall risk badge, and the healing trend.

4  AI analysis pipeline

Three deep-learning models cooperate. Models 2 and 3 share a single frozen CLIP ViT-B/32 image encoder, evaluated once per image, so the installed footprint stays small and inference stays fast. Full method, training and evaluation detail is in the companion three-model technical reference; the summary:

#ModelOutputApproachHeadline
1Wound Segmentation & Measurement pixel mask → length / width / area U-Net + MobileNetV2Test Dice 0.818
2Tissue Classification 5 tissue types present in the wound bed CLIP ViT-B/32 (frozen) + SVM headAUC 0.825 · F1 0.733
3Infection & Ischaemia infection + blood-flow status → risk badge CLIP ViT-B/32 (shared) + MLP headInfection AUC 0.890 · Ischaemia AUC 0.987
Table 2. The three deployed models. See the technical reference for datasets, training schedule, metrics and limitations.

4.1  Measurement post-processing

The mask is binarised, cleaned with morphology, and reduced to its largest component. Length and width are the extents of the wound's principal (PCA) axes — the minimum-area rectangle, not an axis-aligned box — and area is the wound-pixel count scaled to cm². Because the app runs uncalibrated (no reference object), centimetre values are approximate and the reliable healing signal is the relative area trend over time. Wound depth is not produced — a single 2-D photograph cannot recover it.

Parity

The on-device Dart post-processing and the server's Python post-processing are ported one-to-one, so the same photograph gives the same numbers whether analysed offline or online. Both now emit wound area.

5  Architecture, sync & deployment

5.1  How the pieces connect

  • App → API. The Flutter app talks to a Laravel 12 REST API at https://diafootcare.tech/api/v1 (token auth). Guests work entirely offline; registered patients sync their scans and records up to the server.
  • Online analysis. For online mode the API forwards the photo to the FastAPI inference sidecar, which runs the three models and returns the analysis; the API relays it to the app and stores it against the patient.
  • Dashboard. The Vue SPA consumes the same API to present the cohort to clinicians.
  • Local-first. The app keeps a local SQLite history so every feature works without a network; sync reconciles when connectivity returns.
